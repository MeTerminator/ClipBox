# 后端架构

本文说明 ClipBox Go 后端的边界、依赖方向和扩展规则。它描述的是当前实现，不是脱离代码的目标蓝图。

## 设计目标

- 保持单体部署，避免为当前规模引入微服务和复杂框架。
- 业务规则只实现一次，HTTP、WebSocket 和后台任务不得各自复制。
- 文件落盘、数据库持久化和实时广播可以独立测试和替换。
- 保持 SQLite/MySQL、旧数据库迁移以及现有 HTTP API 的向后兼容。

## 依赖方向

```text
main.go（组合根）
  ├─ config ─────────────── 配置读取与校验
  ├─ store.GORMStore ────── SQLite/MySQL、迁移、仓储实现
  ├─ upload.Manager ─────── 分片、校验、本地文件存储
  └─ server.Server ──────── HTTP/WebSocket 适配器
       └─ share.Service ─── 房间认证与消息规则

model <── store / share / server
```

依赖只允许从入口和适配器指向内部规则。`model` 不依赖 Gin、GORM 驱动或文件系统；`share` 不依赖 Gin；`server` 不直接创建数据库连接。`main.go` 是唯一的组合根，通过 `server.Dependencies` 显式装配能力。

## 包职责

| 包 | 负责 | 不负责 |
| --- | --- | --- |
| `internal/config` | 默认值、JSON、环境变量覆盖、校验 | 业务逻辑、全局配置单例 |
| `internal/model` | 持久化实体、无 I/O 的实体判断 | HTTP 请求结构、数据库查询 |
| `internal/store` | 仓储接口、GORM 实现、事务、迁移 | HTTP 状态码、文件上传协议 |
| `internal/upload` | 上传会话、并发分片、SHA-1 校验、原子落盘 | Clip 取件码、数据库记录 |
| `internal/share` | 成员认证、消息校验、实时 fan-out | Gin 路由、响应格式 |
| `internal/server` | 路由、输入解码、错误映射、输出格式 | 驱动选择、数据库连接、重复业务规则 |

`store.Store` 与 `store.RoomStore` 分开是有意的接口隔离：仅使用取件码功能的测试或嵌入场景不必实现房间仓储。房间能力在组合根显式传入；为 `nil` 时对应接口返回 501。

## 核心流程

### 内容取件

创建文本或链接时，HTTP 层完成协议解码和基础格式检查，仓储在唯一索引冲突时返回 `store.ErrConflict`，服务端重新生成五位码。取件分为两类：`info` 只读元数据；`resolve` 和旧版重定向接口通过 `ConsumeByCode` 在事务中扣减一次访问次数。

### 文件上传

1. 客户端提交文件名、大小和预期 SHA-1。
2. 先查数据库与已存文件，命中则创建新的 Clip 记录并复用物理文件。
3. 未命中时，`upload.Manager` 创建或恢复以 SHA-1 为键的会话。
4. 每个分片按精确长度原子写入；完成时重新计算整个文件 SHA-1。
5. 校验通过后才从临时目录发布到 `data/files`，然后创建数据库记录。

数据库中的 `File` 是逻辑元数据；多个 Clip 可以引用同一路径。清理任务只有在引用数为零且路径位于 `DataDir` 内时才删除物理文件。

### 分享房间

HTTP 负责创建、加入和管理，WebSocket 负责实时命令。两种传输共用 `share.Service` 做 token 摘要认证和消息校验。消息先持久化再广播；慢客户端丢失实时事件后，通过消息历史恢复。最后一个在线连接离开时房间被删除，后台任务兜底清理从未连接的空房间。

## 数据一致性与安全边界

- 访问次数的检查与扣减必须在同一事务中。
- 上传成功以服务端重新计算的 SHA-1 为准，不能信任文件名、声明大小或客户端摘要。
- 对外文件名必须先净化；任何删除路径必须再次验证位于 `DataDir`。
- 成员 bearer token 不入库，只存 SHA-256 摘要。
- 自动迁移必须保持幂等；破坏性 schema 变更应改用显式版本迁移，而不是继续扩充启动时回填。
- SHA-1 在这里用于内容寻址和损坏检测，不用于密码学认证。

## 扩展规则

新增能力时按以下顺序判断位置：

1. 与 HTTP/JSON/WebSocket 有关：放 `server`。
2. 与文件分片和本地落盘有关：放 `upload`。
3. 与查询、事务或迁移有关：放 `store`。
4. 同一规则会被多个传输调用：提取到独立应用服务（参考 `share.Service`）。
5. 只有数据和无 I/O 判断：放 `model`。

不要建立 `utils` 或 `common` 包。共享代码应以它表达的领域概念命名，并由使用方定义最小接口。当前代码量下不拆微服务；只有当部署、扩缩容或数据所有权确实独立时再考虑进程边界。

## 已知演进方向

- `internal/store/gorm_store.go` 同时包含连接、迁移和 Clip 仓储。只有当其中一部分继续明显增长时，再按 `database.go`、`migrations.go`、`clips.go` 拆分；不要为了目录看起来复杂而提前增加包层级。
- Clip 创建、解析和上传编排若出现第二种传输，应像房间逻辑一样提取 `clip.Service`；目前只有 Gin 使用者，暂不增加无收益的抽象层。
- 当前 WebSocket hub 是单进程内存广播。多实例部署前必须引入共享 pub/sub，并明确房间删除的分布式一致性策略。
